# IMPLEMENTATION_PLAN.md
Project_Star 实现计划。与 `AGENTS.md`（需求）、`docs/ARCHITECTURE.md`（架构）配合使用；术语定义见 `docs/GLOSSARY.md`。

## 实施约定

- 实现分 7 步（地基属性实体 → 通用机制 → 全局层 → 对局层 → 战斗层 → 三层串联 → 表现层 UI），自底向上推进。
- **每步实施前必须向用户确认**：该步逻辑完全理解、疑问清零、形成闭环后，方可进入实现。
- 实施过程中遇到不理解的点，先提出讨论，不猜测推进。
- 每步完成标准：`dotnet build` 通过；纯逻辑部分配单元测试（价值公式 / 推挤算法 / Resolver）。

## 实现步骤

### 第 1 步：地基——属性与实体

- 状态容器：对局资源 AttributeSet + 战斗状态 BattleState，ApplyModifier / RemoveModifier。
- 实体基类 `HeroBase` / `CardBase` / `EventBase`（身份字段 get-only，key 用 StringName）。
- 反射模板池 `PoolBase<T>`。
- **完成标准**：`dotnet build` 通过。

### 第 2 步：通用机制——事件总线 + 能力/效果

- 局外 `MatchEventBus` / 战斗内 `CombatEventBus`（两套分离，互不互通）。
- 能力基类（主动 / 被动触发）、效果基类。
- 效果堆叠约定：Apply 累加 / 到期扣减 / 不清零 / 抵消判定。
- **完成标准**：`dotnet build` 通过。

### 第 3 步：全局层——管理器 + 卡牌经济

- `HeroManager` / `CardManager`：模板池、实例化、玩家卡池、归属 key 过滤。
- 卡牌价值公式（价值系数 × 等级 × 型号系数）、获得折半、购买全额计价、出售按现值回补。
- **完成标准**：`dotnet build` 通过；价值公式配单元测试。

### 第 4 步：对局层——棋盘 + 轮次事件

- 推挤算法（纯函数：评估 / 执行分离、择优）。
- `GameBoard` 纯数据（战场 + 备战各 10 格）+ `BoardManager`（操作协调、跨区，随对局创建 / 销毁）。
- 轮次调度（8 回合 / 轮）、事件排程（默认三选一含商店 / 第 4 回合三怪物 / 第 8 回合 PvP）、事件执行、商店交易。
- **完成标准**：`dotnet build` 通过；推挤算法配单元测试。

### 第 5 步：战斗层——时钟 + 解析器

- `BattleClock` 两层帧推进（时间推进层 / 逻辑结算层）。
- `Resolver`：逻辑步 8 步序、能力队列（深度上限）、状态周期结算、坍缩 / 寂灭、死亡判定。
- 战斗生命周期（派生初始值 → 主循环 → 收集永久变化 → 丢弃状态）、BattleResult。
- **完成标准**：`dotnet build` 通过；Resolver 配单元测试。

### 第 6 步：三层串联

- `GameManager` 主状态机（选英雄 → 局内 → 结算）。
- `MatchManager` 触发战斗、结束回传（奖励 / 惩罚、应用永久变化、声望扣减 / 胜场累计）。
- 对局胜负判定：10 次 PvP 胜利 / 声望 ≤ 0。
- **完成标准**：对局闭环可运行。

### 第 7 步：表现层——UI

- 选角界面、局内界面、棋盘视图（像素换算）、卡牌展示。
- **完成标准**：最小可玩版本。

## 全程约定

- 目录：Core / Systems / Match / Combat / Entities / UI。
- 提交遵循 `<type>(<scope>): <subject>`。
- 能力复用约定：能力必须可复用，禁止为单张卡写专属能力；卡牌组合已有能力。
- 词条不进入代码逻辑，仅作需求语义概念。
