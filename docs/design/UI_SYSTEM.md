# Project_Star UI 系统设计

版本：v2，2026-09-30。状态：P0 已整理，P1 流程与统一刷新已实现并通过104项Godot验证；P2场景组件与新布局尚未实施。

用户已确认优先级：**先拆分 UI 架构、组件和数据刷新逻辑**。本方案覆盖选英雄至对局结束的完整试玩流程，实施任务见 [UI 实施计划](../planning/UI_IMPLEMENTATION_PLAN.md)。玩法以 [GAME_DESIGN](GAME_DESIGN.md) 为准，术语以 [GLOSSARY](GLOSSARY.md) 为准，分层遵守 [ARCHITECTURE](../engineering/ARCHITECTURE.md)。

**布局依据：** 2026-09-30 用户提供的右侧线框图是本项目目标布局；左侧竞品截图用于观察卡牌与详情的呈现关系。采用顶部轮次栏、下方三行三列、中央内容对齐的结构；用户进一步确认金钱和收入放在顶部右侧。该结构替代 v1 的常驻左侧构筑栏、右侧详情栏与底部操作栏。草图的黑底白线表达区域划分，美术颜色仍按既有方向另行细化。

## 1. 设计基线与目标

| 项目 | 设计基线 | 状态 |
|---|---|---|
| 表现形式 | Godot Control 组成的 2D 对局界面 | 现有实施计划已确认 |
| 主布局 | 顶栏显示轮次，右侧显示金钱/收入；上排切换遭遇/商店/敌方战场，中排为我方战场，下排为备战区；头像和信息分列左右 | 用户草图及补充确认 |
| 美术方向 | 奇幻插画、明亮白金与天蓝；现有卡框、原画和徽章作为卡牌组件基础 | 既有方向；具体主题参数见第 8 节提案 |
| 卡牌规格 | 小/中/大型占 1/2/3 格；同一行等高，宽度比 1:2:3 | 既有规则 |
| 数据边界 | 输入交应用用例；界面读取 Snapshot / ViewModel；卡面不计算战斗结果 | 既有约束 |
| 优先顺序 | 职责拆分 → 快照与刷新 → 组件 → 棋盘与流程 → 战斗表现 → 视觉验收 | 本次用户要求 |
| 输入与窗口 | 首版桌面鼠标、键盘；1920×1080 为主要排版稿，1280×720 为最低验收窗口 | 本方案建议 |
| 战斗呈现 | 一次确定性结算，再播放只读表现数据；提供暂停、1×/2×、跳过 | 本方案建议，需在战斗阶段确认 |

完成后的界面应让玩家能直接判断：当前阶段、可执行操作、卡牌实际占格、操作成本与结果。购买、事件奖励、合并、移动、战斗结算之后，资源、棋盘、详情和按钮状态必须来自同一次刷新。

## 3. 职责拆分与数据流

### 3.1 四个明确边界

| 单元 | 持有与负责 | 对外接口形态 |
|---|---|---|
| `MinimalPlaytest` 根节点 | 创建服务、取得子视图、组装 `MatchPresenter`、连接与释放事件 | `_Ready` / `_ExitTree` 等生命周期 |
| `MatchPresenter` | 调用应用用例、推进显示页面、保存当前操作上下文；持有 Session 句柄供服务调用 | 购买、移动、选遭遇、领取、开始战斗等明确方法 |
| Snapshot → ViewModel 适配 | 将应用层只读查询结果转成文本、贴图和显示状态；复用效果格式化 | `Build…ViewModel` 一类普通 C# 方法 |
| 场景组件 | 布局、绘制、焦点、命中检测、发出用户意图 | `Render(viewModel)` + 明确事件 |

`MatchPresenter` 可以调用现有 `GameCoordinator`、`BoardService`、经济及遭遇服务；Session 中的集合仍由应用层读取和修改。子视图不接收 `MatchSession`、`CardInstance` 或可变的 `ShopStock`。

```text
玩家点击 / 拖拽
    ↓ 明确的操作参数：EntityId、BoardZone、目标格、遭遇 key 等
组件事件 → MatchPresenter → Application 用例 → Domain
                                ↓ Result
                    统一取得本次只读展示快照
                                ↓
                    生成完整页面 ViewModel
                                ↓
               HUD / 内容面板 / 棋盘 / 详情同步 Render
```

现有服务调用可以承载 Command 意图，不要求增加通用命令总线、全局事件总线或万能 UI 管理器。拆分应伴随实际职责迁移，避免只把同一段逻辑转发到更多类中。

### 3.2 页面状态与局部交互状态

| 状态 | 所有者 | 生命周期 |
|---|---|---|
| 金钱、卡牌、位置、奖励、对局进度 | `MatchSession`，由应用服务维护 | 当前对局 |
| 商店访问及商品售罄状态 | 应用层商店上下文 | 当前商店访问 |
| 当前显示页面、操作进行中 | `MatchPresenter` | 当前页面/命令 |
| 选中、悬停、拖拽目标、详情展开 | 表现层 `UiState` | 操作或页面；实体消失时清理 |
| 战斗初始展示、事件列表、结算后快照 | 应用层返回的只读数据包 | 本场战斗 |
| 播放位置、播放速度、表现动画 | `BattlePlaybackPresenter` | 本次播放 |

页面类型建议为：英雄选择、遭遇选择、商店、普通事件、战斗准备、战斗播放、战斗结算、对局结束。页面切换只在用例成功后发生。显示方法不得顺带清除商店、奖励或敌方上下文。

### 3.3 刷新约定

1. 用户输入经过当前页面的可操作性检查，提交一次应用用例；提交期间阻止同一操作重复进入。
2. 成功时调整显示页面，调用一个 `RefreshView` 入口；失败时保留有效选择并展示 `Failure`，需要时重新读取操作条件。
3. `RefreshView` 取得一个一致的查询结果，然后构造全部相关 ViewModel。禁止资源栏、棋盘和详情各自在不同时间读 Session。
4. ViewModel 同时包含内容、可见性、按钮是否可用及不可用原因。切换准备页时，敌方数据和面板可见性在同一次 Render 中生效。
5. 根据新快照校验选中、拖拽、悬停的 `EntityId`。合并、出售、永久摧毁、重开后，不允许引用已移除实体。
6. 视图以 `EntityId` 保留仍存在的节点，仅更新变化字段；资源按 key 缓存。初版使用局部对比即可，不先建立通用虚拟 DOM 或对象池。
7. `Resized` 只触发布局重算；鼠标移动只改变悬停/预览；二者不重建对局、不重新抽商品、不提交命令。没有输入和状态变化时不逐帧刷新卡面。
8. 切换场景、重开、退出时释放订阅，取消拖拽与延迟提示，清空播放和选择状态。

## 4. 只读数据接口

以下接口为目标职责，可扩展现有 Snapshot 或增加小型查询结果；P0 的职责名称、字段来源与缺口见 [职责与展示契约](../planning/UI_P0_CONTRACT.md)。

| 消费组件 | 需要的数据 | 当前基础与待补项 |
|---|---|---|
| 顶栏、英雄区、成长信息区 | 当前轮回合、金钱/收入；英雄身份；声望/经验/等级；其余对局摘要 | 复用同一次 `MatchSnapshot`，按固定区域拆成 ViewModel；经验不推导尚未定义的升级规则 |
| 棋盘 | 区域、容量、每张卡的 `EntityId`、起止格、是否可交互、卡牌展示数据 | 复用 `BoardPlacementSnapshot`，增加容量；占用格数与卡牌数量分别计算 |
| 卡面与详情 | 身份、等级、当前价值、基础与当前效果、触发条件、标签、冷却/魔法需求、任务进度 | 扩展应用层只读查询；详情读取实例当前数据与对应等级能力，图片仍由表现层映射 |
| 商店 | 本次商品定位、报价、是否售罄、可购买/合并条件、刷新费用和可用性 | 将 `ShopStock` 转成只读展示快照；旧商品点击必须能识别过期上下文 |
| 普通事件 | 选项、成本、已知收益、是否可执行、失败原因、结果摘要 | 包装现有 `EncounterOptionSet` / Result；查询不得消耗随机状态 |
| 技能/套装/任务 | 技能身份与等级、能力摘要；套装不同 key 计数与阈值；任务进度及解锁状态 | 技能和任务已有部分 Snapshot；套装计数复用现有领域求值 |
| 放置预览 | 源实体、目标格、成功/失败、推挤方向、所有受影响实体的目标位置 | 在 `BoardService` 增加只读预览，复用 `BoardPlacementSolver` |
| 战斗播放 | 战前卡牌身份与位置、双方初始战斗 HUD、有目标标识的变化记录、战斗结果、结算后快照 | 新增完整表现数据契约，见第 7 节 |

数据规则：

- 静态内容 key 使用 `StringName`，卡牌实例使用 `EntityId`。同 key 的多张卡不能共享一个视图身份。显示文本使用 `string`。
- 查询返回独立的只读数据，不将可变集合或领域实体包装成 `IReadOnlyList` 后直接泄露给 UI。
- 价值显示与出售用例采用相同数值口径；商品购买价与拥有卡牌的当前价值分别标明。
- 基础值、对局加成和战斗中临时值必须区分。构筑页不把等级基础值冒充当前值，回放页不读取已经结算后的实例重算过去状态。
- 应用层/领域层复用已有属性求值；表现层只格式化数值和语义。诸如“敌方最大生命的 20%”“随己方当前生命变化”的效果保留百分比/条件，不预先伪造最终伤害。
- 能力文案按通用效果类型生成；数值取当前等级定义或实例查询。正式 CSV 用于核对规则，不在 UI 再手写一份逐卡数值表。首版覆盖当前正式能力，无法表达的效果须在验收前补齐通用格式化。
- 原画映射使用完整 key，例如 `new StringName("card.armguard")`。映射表只保存视觉资源，不携带玩法能力。缺图使用统一占位纹理。
- 放置预览不修改棋盘、不消耗随机状态；提交时重新校验最新状态，不能直接提交可能过期的预览。

## 5. 组件与场景结构

```text
Playtest.tscn                        MinimalPlaytest：组装入口
└─ MatchShell                       场景排版根
   ├─ TopBar                       左侧轮次；右侧金钱 / 收入
   ├─ ContextRow                   上排
   │  ├─ ContextPortrait           敌方 / 商店 / 遭遇头像
   │  ├─ ContextHost               同一位置切换阶段内容
   │  │  ├─ HeroSelectionView / EncounterChoiceView
   │  │  ├─ ShopView / EventView
   │  │  ├─ OpponentBoardView      复用 BoardZoneView
   │  │  └─ ResultView             战斗结算 / 对局结束
   │  └─ LeavePanel                当前阶段允许的离开操作
   ├─ BattlefieldRow               中排
   │  ├─ LeftReserved              空白保留
   │  ├─ PlayerBoardView           复用 BoardZoneView
   │  └─ RightReserved             空白保留
   ├─ BenchRow                     下排
   │  ├─ PlayerHeroPanel           英雄头像
   │  ├─ BenchBoardView            复用 BoardZoneView
   │  └─ PlayerProgressPanel       声望 / 经验 / 等级
   └─ OverlayLayer                 详情、放置预览、提示、确认框
```

三个内容行共用左右列宽与中央列边界，不能让各行按子节点的最小尺寸分别挤压列宽。`ContextHost` 只显示当前阶段的一个内容视图；准备和播放时在其中显示敌方棋盘。头像、内容和离开条件由同一页面模型同步切换。技能/套装/奖励等二级内容仍保留功能需求，入口位于左下英雄区，打开二级浮层；任务放卡牌详情，不占用两个空白格。

结构图表达职责，页面可按需实例化；只建立当前阶段实际使用的组件。棋盘与商品中的卡牌组成如下：

```text
CardItemView                        引用只读卡牌模型，维护交互状态
├─ CardFace                         现有统一卡面，输入 CardFaceViewModel
├─ InteractionOverlay              悬停、选中、拖拽、不可用提示
└─ BattleOverlay                   冷却、状态、发动反馈（战斗阶段加入）
```

`CardFace` 继续负责 [卡面规范](CARD_FACE_UI.md) 中的卡名、等级、原画、元素、五类效果和价值。身份来自属性集的只读快照，视图不在 Node 上另建一份可修改的卡名、归属或尺寸。描述、标签、冷却详情进入详情组件；战斗冷却环或进度条属于卡牌外层，不混入通用卡面的字段。鼠标命中由 `CardItemView` 统一接收，装饰子节点忽略鼠标，避免徽章挡住点击。

建议文件归属：

| 目录/文件 | 内容 |
|---|---|
| `scripts/Presentation/MinimalPlaytest.cs` | 保留现有场景入口，逐步缩为组装与生命周期 |
| `scripts/Presentation/Playtest/` | `MatchPresenter`、`UiState`、页面 ViewModel 与流程子视图 |
| `scripts/Presentation/Board/` | `BoardZoneView`、布局换算、拖拽/点击输入 |
| `scripts/Presentation/CardFace/` | 复用现有卡面子模块，加入卡牌交互外层、详情与展示适配 |
| `scripts/Presentation/Combat/` | 播放协调器、战斗 HUD 与事件表现 |
| `scripts/Presentation/Common/` | 真实复用的操作反馈、确认框、主题引用 |
| `scripts/Application/Match`、`Board`、`Economy`、`Combat` | 对应只读查询、预览、事务及战斗表现数据输出 |
| `art/ui/` | 主题、纹理、图标和只读视觉资源映射 |

所有 C# 与 `.cs.uid` 留在 `scripts/`。`Main.tscn` 继续承载规则验证，`CardFaceShowcase.tscn` 用于卡面组件展示；对局界面通过开发入口进入规则验证。新组件类型避免与命名空间末段同名；引用现有 `CardFace` 类型时使用明确别名。

## 6. 排版与输入

### 6.1 用户确认的区域结构

```text
┌─────────────────────────────────────────────────────────┐
│ 轮次 / 回合                                金钱 / 收入   │
├──────────┬─────────────────────────────────┬────────────┤
│ 敌方头像 │ 敌方战场 / 遭遇界面 / 商店界面   │            │
│ 商店头像 │                                 │ 离开按钮   │
│ 遭遇头像 │          上层内容切换区         │            │
├──────────┼─────────────────────────────────┼────────────┤
│          │                                 │            │
│ 保留空白 │          我方战场区             │ 保留空白   │
│          │                                 │            │
├──────────┼─────────────────────────────────┼────────────┤
│          │                                 │ 声望       │
│ 英雄头像 │            备战区               │ 经验       │
│          │                                 │ 等级       │
└──────────┴─────────────────────────────────┴────────────┘
```

左上三个头像名称表示按阶段三选一，实际只显示当前对象的一个头像。左下英雄头像和右下成长信息位置稳定；中排两侧保持留白。主框的边线是排版边界，最终美术可以使用面板、留白和细线表达。

| 区域 | 位置与内容 | 布局约束 |
|---|---|---|
| 顶栏 | 左侧第 N 轮/第 N 回合；右侧金钱与收入 | 横跨三列；声望/经验/等级放在右下 |
| 场景头像 | 左上，显示敌方、商店或已进入遭遇的头像 | 缺图时统一占位；与上层内容一同切换 |
| 上层内容 | 中央上排，显示敌方战场、遭遇选择、商店或事件 | 共享同一块区域，不再另外增加敌方战场行 |
| 离开区 | 右上，显示本阶段允许的离开/继续操作 | 保持按钮位置；具体是否可用由阶段与应用用例决定 |
| 我方战场 | 中央中排，10 格 | 与上排敌方棋盘、下排备战区共用横向标尺 |
| 英雄头像 | 左下，显示当前英雄 | 英雄相关战斗信息使用该组件的关联展示，不迁移到顶栏 |
| 备战区 | 中央下排，10 格 | 与我方战场固定上下关系 |
| 成长信息 | 右下，依次显示声望、经验、等级 | 同次快照刷新；经验升级规则以现有玩法为准 |
| 两侧空白 | 中排左右 | 当前保留；新增功能占用前需单独确定 |

草图的宽度比例约为 **左 17% / 中 66% / 右 17%**，顶栏约占总高度的 20%～23%，下方三行接近等高。这些比例只作为排版初值：实际需扣除页边距、区标题和操作控件，再根据卡牌比例确定行高。1280×720 的字号与命中目标必须单独验收，不能将整张草图作为一张图片缩小。

购买、刷新、选项、确认英雄、开始战斗放在对应上层内容内；右上按钮专门承载离开/继续。暂停、倍速、跳过属于播放控件，不能被误解为退出战斗。操作失败显示在触发位置，日志从可展开浮层查看，不再设置独立底部操作栏。

详情采用卡牌附近的浮层：悬停或主动查看时显示，包含放大卡面、效果、标签、冷却与任务等内容，并根据视口边缘翻转或限位。浮层不重新分配三列宽度、不挤动棋盘、不截获背后无关卡牌的鼠标；长内容仅在浮层内部滚动。竞品截图可用于理解这种信息层级，原画、图标和具体数值仍使用本项目内容。

准备阶段允许调整双棋盘；播放时展示冻结的阵容，操作门控使对局命令不在播放期间进入。备战区可查看，战斗表现不将其视为参战区。结算展示本场胜负、金钱/经验变化、声望或 PvP 胜场变化、待领取奖励；对局胜负有独立结尾页。

双方生命、护甲、魔法和状态作为对应头像组件及棋盘内部信息条的关联展示，在 P5 细化；不为战斗再插入一整行外部区域。技能、套装、PvP 胜场、待领奖励等入口位置未在草图中指定，P0 需补充细节，功能数据契约仍保留。

P5 已实施：双方头像关联区域显示生命、护甲、魔法、灼伤和中毒；卡面插画区域叠加剩余冷却及疾速/迟缓/禁锢，发动短暂提亮，摧毁变暗并保留身份。右下显示最近四条伤害、治疗、护甲、充能与摧毁反馈。暂停、1×/2×、跳过放在右上操作区最前，播放中隐藏开发入口；跳过只消费剩余冻结记录，不结算或领取奖励。多种并存状态在紧凑卡面可能省略，完整内容保留在卡牌提示中。主题及所有窗口适配仍归 P6。

P6 已实施：统一使用 `MatchTheme` 白金面板、天蓝交互、深蓝文字；容器间距8px、基准字号16px、紧凑卡面字号最低13px。基准及最小试玩窗口1280×720，`canvas_items` 配合 `expand`，标准比例整体放大，超宽扩展留白而不改变三个棋盘共用格宽。卡牌选中带“选”标记与金色轮廓；焦点和悬停分别使用粗、细蓝框；获取、合并、移动和选中短暂强调，不移动命中区域。开发入口默认折叠，结果日志由开发区打开；播放控件保持直接可见。四种分辨率截图与原生窗口/键盘验证见 `docs/quality/MANUAL_ACCEPTANCE.md`，完整人工整局仍归 P7。

### 6.3 卡牌与棋盘的尺寸契约

- 棋盘以逻辑格宽 `u` 为基准，容量为 `C`。卡牌 `Start = s`、占格数 `n`，其交互范围为 `x = origin + s × u`、`width = n × u`；同一行卡面高度为 `2 × u`。小/中/大型始终保持 1:2、1:1、3:2 的外轮廓比例。
- 每个放置实例只生成一个完整卡牌视图；格底与格线独立绘制。中大型卡的任意部分都能命中同一 `EntityId`，不会出现后续格只是一块占位按钮的情况。
- 可用区域为 `W × H` 时，`u = min(W / C, H / 2)`，棋盘整体居中。相邻卡牌用框线/内描边区分，间隙不额外改变逻辑占格宽度。坐标换算使用实际 Control 变换和区域原点。
- 建议三条棋盘轨道从 `u = 100`、高度 200 起调；各行扣除标题/操作区后，以最小可用尺寸求共同格宽，使敌方、我方和备战区的格线对齐。详情放大展示保留原始 200/400/600 × 400。具体数值通过实际窗口验收调整，同一区域所有尺寸共用高度。
- 卡面应按目标尺寸排版，字体和徽章设置最小可读尺寸；不能依赖整体 `Scale` 将全部文字一同压小。主卡名以 14px 为最低验收值，信息过长可省略并在详情中完整呈现。
- 窗口缩小时保留三列三行关系，先压缩留白和头像装饰，再按共同格宽调整卡牌区域；1280×720 仍需同时看到双方战场、备战区及当前操作。关键棋盘不横向滚动。
- 各窗口均采用详情浮层，固定右下区域用于声望/经验/等级。超宽窗口保持主体最大宽度，额外空间用于背景，避免卡牌横向拉伸。

### 6.4 交互约定

| 输入/场景 | 行为 |
|---|---|
| 悬停 | 延迟显示详情和可操作提示；不改变棋盘位置 |
| 点击我方卡牌 | 选中并标记完整占格范围；详情同步显示 |
| 已选中后点击目标格 | 以该格为起始格，请求放置；保留现有点击移动能力 |
| 拖拽 | 超过阈值才开始拖拽；保存抓取格相对卡牌起始格的偏移，预览完整范围和被推挤卡牌 |
| 拖到边界外/非法区间 | 红色轮廓加具体文字原因；松手后取消，原数据不变，不静默改为另一目标格 |
| 放置成功 | 依据 Result 的完整移动列表更新表现，随后与新快照对齐 |
| 右键 / Esc | 依次取消拖拽、选中或关闭当前浮层；无局部状态时由当前页面处理 |
| 购买 | 点击商品的购买按钮提交一次；点击卡面本身查看详情；显示费用、售罄或不可购原因 |
| 出售 | 从选中卡牌的操作浮层点击出售，再确认卡名与当前价值；应用用例一次完成移除、回补和出售奖励 |
| 键盘焦点 | Tab 导航操作控件，Enter/Space 只激活已有焦点的按钮；可见焦点框 |
| 重开 | 明确确认将结束当前对局；成功后重建对局上下文并清空局部交互状态 |

普通错误保留上下文，例如金钱不足、两区已满、不可推挤、商品已售罄。失败禁用态同时提供文字原因。选中与失败使用轮廓、图标和文案表达，不只依赖颜色。

## 7. 页面与操作契约

| 页面/区域 | 显示与操作 | 必须处理的边界 |
|---|---|---|
| 英雄选择 | 按注册定义生成英雄选项，展示初始属性，确认后创建一局 | 无英雄、重复确认；不假定永远只有一名英雄 |
| 遭遇选择 | 按实际候选数绘制，展示类型与当前轮回合 | 少于三个候选；第 4 回合怪物和第 8 回合 PvP |
| 商店 | 同一卡面、购买价、合并提示、售罄、刷新费用、离开 | 金钱不足、满盘但可合并、不可刷新、旧报价点击；随机由应用层执行 |
| 普通事件 | 按实际选项数生成成本/效果按钮，执行后展示结果摘要 | 失败不推进；卡牌奖励与加成同步刷新；未知随机收益不预抽 |
| 奖励 | 待领数量、卡牌/技能详情、领取结果 | 两区已满时保留奖励；领取合并；末局奖励按应用层允许的操作展示 |
| 构筑摘要 | 技能列表、套装阈值、任务进度 | 技能不占格；套装以战场不同 key 计数；没有内容时显示空状态 |
| 战斗准备 | 敌我英雄与战场、备战、战斗类型、开始按钮 | 空战场提示但允许开始；敌方可见性与数据同时刷新 |
| 战斗结算 | 本场结果、资源差额、待领取奖励、下一步 | 战斗胜利与对局胜利区分；怪物失败不显示声望扣除 |
| 对局结束 | 胜负、PvP 胜场与对局摘要、返回英雄选择 | 禁止旧对局继续操作；重开无残留 |

经济操作有两个接入前置条件：当前 `BuyCard` 后的放置仍由试玩脚本编排；当前 `SellCard` 会拒绝仍在棋盘上的卡牌。实现商店 UI 时，应用层需提供完整的“购买/合并/放置”和“从棋盘出售”事务入口。不得由视图先移出棋盘再试出售，也不得在扣款成功后留下未放置卡牌。

### 战斗表现的数据前置条件

建议保留“先计算、后播放”的确定性边界。当前 `GameCoordinator.ResolveBattle` 已经执行结算；新增接口应一次返回战前展示输入、`BattleResult` 和结算后快照，使播放结束或跳过只切换视图，不重复调用结算。

P5 必须补齐并验收：

1. 战前捕获双方英雄的初始生命/护甲/魔法/状态，以及卡牌身份、位置和初始冷却。
2. 治疗、护甲、魔法、状态施加/衰减/到期、冷却变化/充能、卡牌摧毁有可定位的实体/方位与结果值。现有事件不足时，由战斗层在真实变化点补事件或只读时间点快照。
3. 相同 Tick 保持战斗日志原始顺序。动画可以插值，数值只取记录结果；表现层不另写一份战斗规则计算缺失状态。
4. 冻结的战前身份仍能展示已被永久摧毁的卡牌；其在结算后的移除只由应用结果体现。
5. 暂停、倍速、跳过均不改变 `BattleResult`、不再次发奖。进入结算页时一次呈现结算后快照。
6. 对现有结果和事件顺序建立回归基线；补日志可增加事件，但既有事件相对顺序、战斗数值和结果必须保持。

| 项目 | 建议规范 |
|---|---|

## 9. 实施边界与评审点

P0 契约见 [职责与展示契约](../planning/UI_P0_CONTRACT.md)。P1 已拆出 MatchPresenter 与完整 MatchPageViewModel：根节点组装服务并 Render，所有应用操作经统一 RefreshView；卡牌快照提供基础/当前属性、能力与任务，技能提供能力与当前属性，应用展示查询补充套装阈值及购买条件。CardDisplayAdapter 统一格式化卡面与工具提示详情，并缓存完整 key 的原画和缺图占位。P2 再拆分子视图和场景布局；经济完整事务仍按P4接入。验证记录见 [人工验收](../quality/MANUAL_ACCEPTANCE.md)。
