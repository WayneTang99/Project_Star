# 异步 PvP：当前服务端实现

更新：2026-10-23。已部署真实玩家快照匹配、持久任务、一次结算和跨轮继续。两个测试账号通过正常购买、事件与怪物战完成两轮，并先后消费对方的真实快照。后续Main已增加[联网操作面板](ONLINE_CLIENT.md)，客户端应用／HTTP适配实测至第二轮；完整棋盘、回放与公网HTTPS尚未接入。后端证据见[P4验证记录](../quality/ASYNC_PVP_P4_2026_10_23.md)，面板验证不等于完整人工对局。

## 1. 状态与所有权

`ServerMatchService`复用正式战斗、成长、任务、奖励、胜场及声望结算。`ServerMatchSession.Pvp`保存战斗ID、发生轮、种子、完整固定对手、来源标记及可空结果摘要。客户端不上传阵容存档，不决定对手、种子或胜负。

正常阶段：`EncounterChoice（第8回合）→ PvpPending → PvpResult → EncounterChoice（下一轮第1回合）`。

选择PvP时，既有遭遇用例已将进度推进到下一轮第1回合；此时不生成新候选，不发新轮收入或经验。战斗结算使用固定的发生轮计算声望及终局统计。只有`finish_pvp`在处理完待领奖励后生成下一轮候选并结算该边界一次。客户端显示本场发生轮应使用`pvp.round`，不能从已推进的`state.round`反推。

`PvpPending`冻结所有棋盘及访问操作。非终局的`PvpResult`允许移动、出售、领取奖励再继续；终局状态保留结果和待领奖励，不再领取或进入下一轮。数据库将终局对局标为`ended`，释放每账号一局限制；旧局仍可按ID查询，新局不覆盖旧结果。主动投降及终局奖励处置尚无联网入口。

## 2. 快照与匹配

- `pvp_snapshots`仅由已成功结算的服务器任务发布，唯一键为对局／发生轮／规则版本；保存参战前状态，不使用战后成长替换旧快照。
- 匹配严格要求相同规则程序集SHA-256、相同发生轮，排除同一内部玩家的全部对局。优先选择本局未遇过的来源玩家；没有新来源时允许重复来源，在同一优先级内随机选择。不跨轮或跨版本放宽。
- 被选中的快照作为独立对手模型冻结进任务，模拟和结算不读取、修改被挑战者的当前对局。对方继续游戏不会改变已接受的任务。
- 空池复用现有`LocalTestOpponentProvider`的受控构筑，按相同轮次生成合法PvP候选。`isTestOpponent=true`且`opponentSnapshotId=null`；真实来源则相反。测试构筑不是已平衡的正式机器人难度，也不能计作真实匹配证据。

快照、任务输入及回执目前保留，尚未实现容量上限、过期清理与归档策略。表间外键和任务固定输入意味着清理不能直接删除仍被引用的快照。

## 3. 持久任务与事务

结构版本3新增`pvp_snapshots`和`pvp_battles`。任务保存原始参战快照、双方冻结存档、输入摘要、种子所在存档、预期对局版本、来源、状态、尝试次数、租约、令牌及最终结果。完整输入只在服务端保存，不通过HTTP下发。

1. **接受参战**：在玩家事务内校验归属、请求幂等、版本和已下发PvP候选；固定对手、战斗ID与输入，写入pending任务、待结算对局和请求回执后提交，返回202。
2. **领取**：单个后台执行器通过`FOR UPDATE SKIP LOCKED`原子领取任务，换新执行令牌，设置60秒租约。当前只执行与运行规则摘要相同的任务。
3. **模拟**：校验冻结文本SHA-256，在SQL事务之外调用Godot规则进程；包含排队的规则调用最多20秒。HTTP请求断开不取消已提交任务。
4. **提交**：重新取得玩家事务锁，校验任务令牌、有效租约、输入摘要、原冻结存档及预期版本；一次提交新对局／版本、战斗结果、开战前快照及completed标记。任一写入失败整笔回滚。
5. **恢复**：过期running任务可重新领取，旧执行器不能用旧令牌提交。技术异常最多自动尝试3次，其间约1秒后重试；耗尽进入failed，不判玩家输、不改原对手或输入。玩家可对failed任务调用`retry_pvp`，重新尝试同一场。

模拟可能重复执行，业务结果只提交一次。`retry_pvp`只改变任务元数据，返回202且不增加对局版本；真正结算增加一次版本。服务停止时未完成的租约保留供恢复，不依赖内存队列。

当前执行并发为1，Godot规则进程也串行运行；怪物战仍沿用同步事务路径。这是小规模正确性实现，没有500人容量证据。

## 4. HTTP 契约

全部接口要求当前账号的Bearer访问凭证；请求回执、冲突与错误外壳见[权威存档](MATCH_PERSISTENCE.md)。

| 操作 | 输入／响应 |
|---|---|
| `POST /v1/matches/{id}/commands`，`type=start_pvp` | `requestId`、`expectedMatchVersion`、已下发`encounterKey`；202，递增版本及`state.pvp.id` |
| `GET /v1/battles/{battleId}` | 200：`battleId`、`status`、`round`、`attempts`、`isTestOpponent`、`opponentSnapshotId`、可空`result`；仅任务所属玩家可读 |
| 同命令接口，`type=retry_pvp` | `requestId`、当前`expectedMatchVersion`、`battleId`；仅failed原任务，202，对局版本不变 |
| 同命令接口，`type=claim_reward` | `requestId`、当前版本、`battleId`、`rewardIndex`；非终局PvP结果或怪物结果，200 |
| 同命令接口，`type=finish_pvp` | `requestId`、当前版本、`battleId`；非终局且待领列表为空，200，下一轮候选 |
| `GET /v1/matches/{matchId}` | 读取本人当前或已结束对局；跨账号404，不兼容规则409 |
| `GET /v1/matches/current` | 仅进行中对局；终局后无新局时404 |

任务status为`pending/running/completed/failed`。completed的`result`包含提交当时的`matchId/version/rulesVersion/state`；以后继续对局不会改写这份历史结果。state中的pvp提供对手英雄／卡牌展示及结果摘要，不提供随机内部状态、原始存档、租约令牌或对手账号身份。

`resolve_pvp`只属于宿主与规则进程之间的私有协议，公网命令白名单拒绝它。客户端提交的额外seed或对手字段不会参与参战。历史`start_pvp`回执仍是原202待结算状态，客户端应继续查同一battleId，并按单调版本更新本地展示，不能用历史低版本响应覆盖新状态。

当前没有`/playback`接口，仅有结果摘要和服务端冻结输入；尚不能称为完整可下载回放。

## 5. 部署与版本边界

当前程序为`/opt/project-star/releases/p4-20261023-pvp-01/host/`，规则摘要与验证证据见[P4记录](../quality/ASYNC_PVP_P4_2026_10_23.md)。数据库结构3、存档格式4。连接、独立数据位置与构建流程分别见[服务器访问](SERVER_ACCESS.md)、[账号运维](ACCOUNT_SERVER.md)、[存档构建](MATCH_PERSISTENCE.md#6-构建与当前部署)。

规则变化后旧局仍保留并返回409；旧版本任务保留，但当前执行器不会执行它们。正式版本路由／迁移政策尚未实现，不能把新二进制部署等同于旧局已能继续。结构3不能直接换回只支持结构2的程序；安装器遇到跨结构迁移后的就绪失败保持新程序并要求向前修复，不自动降级数据库或切回不兼容旧程序。

程序只读发布树与PostgreSQL、备份、外置配置严格分开。日志只记录错误类型与战斗ID；备份留在云端独立数据树，源码、发布包及本地output中不存放真实玩家数据。
