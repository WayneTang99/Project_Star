# 异步 PvP 服务器开发计划

日期：2026-10-22  
状态：P0 执行中，官方专用包与16项机制已在云端通过；完整固定输入矩阵、正式协议与容量验收仍待完成。
目标：先用现有内容建立服务器权威的异步 PvP 可玩切片，再扩充内容；500 人同时在线保留为扩大封测的容量验收目标。

## 1. 文档职责与依据

本文维护服务器开发范围、阶段任务、容量目标、风险和验收门槛，不重复维护卡牌数值与正式玩法。玩法以 [GAME_DESIGN](../design/GAME_DESIGN.md) 为准，术语见 [GLOSSARY](../design/GLOSSARY.md)，分层与状态所有权见 [ARCHITECTURE](../engineering/ARCHITECTURE.md)，总体队列见 [IMPLEMENTATION_PLAN](IMPLEMENTATION_PLAN.md)。

本文中的技术选型、性能阈值和账号方案为实施建议；标注“已确认”的用户决策作为当前范围依据。实施时将正式架构决策更新到架构文档，将新增玩法更新到游戏设计，避免多处维护规则。实际执行证据见[P0首轮记录](../quality/ASYNC_PVP_P0_2026_10_22.md)，不将源码基准视作正式业务部署，不包含服务器凭据。

执行顺序以总体计划为准：M1 对应本文 P0～P4，先跑通小规模邀请试玩；M2 稳定切片与完整人工对局；M3 按试玩反馈扩充内容与整体 UI；M4 对应 P5，完成 500 人容量认证。P0～P4 的正确性、最小安全部署与备份恢复不后移，完整容量认证不阻挡首次可玩切片。

## 2. 已确认条件

### 2.1 业务范围

- 扩大封测以 500 人以内同时在线为目标；首次切片先记录小规模实测人数，当前机器尚未被证明能够承载 500 人。
- 用户要求先通过异步 PvP 做出切片，再补充内容。默认复用现有正常构筑流程与可达内容；新增内容仅在确实阻断闭环时最小补齐。
- 当前没有账号系统，需要新增最小身份与登录能力。
- 使用玩家离线参战快照作为对手，双方无需同时在线。
- 被挑战方的对局进度、声望和胜场不因被挑战而改变。
- 首版按相同轮次随机匹配；对手池为空时使用测试构筑。
- 已开始执行 P0，云服务器用户目录已有隔离验证工具与程序，尚无正式账号、玩家存档／数据库或业务服务。
- 程序与玩家数据必须分开存放；发布、回滚和清理程序不得删除或覆盖存档／数据库。

## 3. 容量判断与网络预算

### 3.1 500 人在线的定义

500 个独立账号维持有效会话，按实际节奏进行构筑、购买、出售、移动、遭遇选择、怪物战和 PvP，并包含回放获取与重连。在线不要求保持长连接；客户端不为维持“在线”而高频轮询。

区分在线人数、每秒请求数、战斗到达速率、战斗执行并发和网络出口用量。不能用 500 个闲置连接通过来代替容量验收。

### 3.2 3 Mbps 是重要约束

按十进制换算，3 Mbps 理论约为 375 KB/s；这是未扣除协议、TLS、重传等开销的上限。平均分给 500 人只有约 750 B/s/人，不能作为每个人可持续获得的保证。

首轮规划暂按理论上限的 70%（约 262.5 KB/s）作为业务出口预算，后续以实测调整：

| 示例负载 | 业务响应体出口，不含协议开销 | 含义 |
|---|---|---|
| 500 人每人每 10 秒一次操作，每次响应 2 KB | 约 100 KB/s | 有一定余量，但还要加登录、战斗及回放流量 |
| 同样频率，每次响应 10 KB | 约 500 KB/s | 已超过套餐理论上限 |
| 50 人同时获取每份 200 KB 的回放 | 共约 10 MB | 单按理论出口需约 26.7 秒，其他请求会竞争带宽 |

以上只是容量算例，不是已经测得的协议体积或玩家行为。300 GB 月流量与 3 Mbps 峰值是两个独立限制，需要同时监控；例如持续 100 KB/s，30 天约产生 259.2 GB 业务流量，实际计费还取决于云厂商口径。

### 3.3 首版网络措施

- 正式客户端与更新包通过独立分发渠道提供，不从这台 3 Mbps API 服务器分发。
- 普通操作返回必要结果和状态版本；完整恢复快照用于登录恢复、冲突恢复等场景，避免每次拖拽都返回完整对局。
- 先测量完整快照与回放体积，再决定压缩、增量字段和分段获取；不预先构建复杂同步框架。
- 战斗回放在客户端播放，不逐 Tick 请求服务器；排队查询采用退避，恢复前台时再查询状态。
- 优先尝试服务端计算结果、客户端用同版本输入复算生成展示；必须验证结果一致、输入规模和兼容策略后才能采用。若采用服务端事件／状态回放，则单独压缩并按需获取。
- 无论回放采用哪种格式，正式结果始终由服务器裁定；客户端复算不提交权威结果。
- 当出口长期饱和或回放等待超标时，优先评估带宽升级／回放独立分发，不能仅增加 CPU。

## 4. 切片范围与后续范围

### 4.1 必须完成

M1 必须完成最小账号、登录、服务器创建对局、完整持久化、重连恢复、切片中全部可达状态修改的应用用例接入、真实对手池、确定性战斗、一次性结算、版本隔离、基础日志、小规模性能记录及一次备份恢复。默认不删现有可达功能；若缩小可选入口，先明确测试范围，不能留下客户端权威旁路。

切片先证明两个账号经正常构筑到首轮 PvP、继续下一轮、真实快照匹配及断线恢复。完整胜利／失败终局、集中人工矩阵和反馈收口安排在 M2。500 人阶梯压测、长时间运行及完整发布／回滚演练安排在 M4；对外扩大规模前必须通过对应门槛。

联网权威对局与本地试玩保持明确模式边界。网络失败不得静默降级为本地权威对局再上传进度。

### 4.2 后续再做

段位和赛季、排行榜、好友、聊天、观战、跨区、多机高可用、复杂战力匹配、支付、第三方账号、邮件与短信验证。首版不引入 Redis、消息中间件或微服务集群；只有测量结果表明需要时才增加组件。

## 5. 现有代码与实施边界

| 现有能力 | 复用方向 | 需要补齐 |
|---|---|---|
| MatchSession 聚合与应用用例 | 服务端拥有对局并执行合法命令 | 存档恢复、操作适配、并发与事务 |
| BattleSetup / CombatSimulator | 冻结输入与确定性模拟 | 跨进程协议、跨平台基线、资源限制 |
| BattleResult 与回放 | 一次结算、重复读取展示 | 持久化及网络传输格式 |
| IDefinitionCatalog / Content Definition | 单一规则和内容来源 | 发布版本与内容指纹 |
| IOpponentProvider | 对手来源扩展点 | 异步流程、匹配上下文、失败与取消 |
| LocalTestOpponentProvider | 本地试玩和测试夹具 | 不作为真实玩家池实现 |

当前项目使用 Godot.NET.Sdk/4.7.2、net8.0，领域数据包含 Godot.StringName。不能因 Domain 不依赖 Node，就认为它能直接在普通 ASP.NET 进程独立运行。先验证真实运行依赖。

当前 IOpponentProvider.CreateOpponent(ulong seed) 是同步接口，且同时承担怪物创建。联网匹配需要账号、对局、轮次、版本等上下文；实现时按实际调用边界调整为异步应用流程，保持怪物本地定义创建的职责清晰，不用同步 HTTP 阻塞 UI。

所有新增 C# 与对应 uid 仍置于 scripts/ 的既有五层下。网络、数据库与进程适配属于 Infrastructure；命令协调属于 Application；领域规则仍在 Domain；服务组装入口遵循现有架构，具体宿主项目布局在 P0 确定。标识性 key 在领域使用 StringName，网络和存储通过显式编码转换，不修改这一约束。

## 6. 建议部署架构

```text
Godot 客户端
    │ HTTPS
Nginx
    │ 本机接口
ASP.NET Core API
    ├─ 身份、授权、命令去重、查询、版本校验
    ├─ PostgreSQL：账号、对局、任务、结果、对手池
    └─ 本机私有通道
         Godot 无界面规则进程
         └─ Application + Domain + Content
```

这是待 P0 验证的首选方案。HTTP API 与规则进程常驻；战斗设置受限并发，不按请求启动 Godot。规则进程崩溃后能够从持久任务和对局重新执行；API 不以进程内存作为唯一事实来源。

最小交互方式是加载已提交状态、执行应用用例、生成候选新状态与结果，再由 API 通过版本条件提交数据库。若采用常驻对局缓存，数据库提交成功后才替换已提交缓存，失败则丢弃候选状态，不能出现内存已扣款而数据库未扣款。

API 与规则进程使用只监听本机的受限通道，不暴露任意方法执行。服务使用独立低权限账号，由 systemd 管理。PostgreSQL 不开放公网。是否容器化在部署验证后决定，首版只保留一种正式部署方式。

ASP.NET 和 Godot 的运行时版本分别核实；根据部署时官方支持周期选择 API 的受支持 .NET 版本，不因客户端使用 net8.0 就默认所有服务必须使用同一版本。

## 7. 最小账号方案（建议）

采用邀请码封闭注册、账号密码登录、短期访问凭证和可撤销的续期会话。邀请码由管理员线下发放，账号身份由服务器生成，展示名与稳定玩家 ID 分开。账号名称归一化和唯一约束在数据库落实。

- 密码使用成熟库提供的带独立盐、自适应成本哈希，不自行设计加密算法，不记录明文密码。
- 登录和注册限流；错误信息避免直接暴露账号是否存在。
- 会话续期凭证仅保存哈希，支持轮换、退出和管理员撤销；具体令牌方式在 P1 决定。
- 客户端通过操作系统安全存储保存长期凭证，不将密码或凭证写入日志。
- 首版提供受保护的管理员重置入口或运维命令；身份核验与重置流程留痕，不提供无验证的自助找回。
- 默认建议每个账号一个进行中的正式对局；同账号多端通过对局版本处理冲突。此产品限制在 P1 前确认。

验收：重新登录能找到原对局；账号 A 无法读取或修改账号 B 的存档、战斗结果及会话；注销后续期凭证失效；数据库与日志中无明文凭据。

## 8. 数据与协议

### 8.0 程序与玩家数据物理分离（硬约束）

| 类型 | 建议位置 | 生命周期与写权限 |
|---|---|---|
| 程序及运行依赖 | `/opt/project-star/releases/<version>/`，当前入口 `/opt/project-star/current` | 发布时创建，服务账号只读，旧版本可独立清理 |
| 玩家文件存档与业务持久文件 | `/var/lib/project-star/` 下按实际职责划分 | 跨程序版本保留；仅对应服务账号可写，不放入发布目录 |
| PostgreSQL 数据 | `/var/lib/postgresql/` 或独立持久卷 | 由数据库账号管理；不位于 Git 工作区、构建或程序目录 |
| 身份保护密钥 | `/var/lib/project-star/auth-keys/`（采用该机制时） | 随数据持久保存并受限访问，避免重发程序使已有会话不可恢复 |
| 配置与凭据 | `/etc/project-star/` | 独立权限，不写入源码或发布包 |
| 日志 | `/var/log/project-star/` 或 systemd journal | 独立轮换与清理，不混入玩家存档 |
| 临时与缓存 | `/var/cache/project-star/` 或受控运行时临时目录 | 可以清理，不作为玩家状态的唯一存储 |
| 备份 | 独立备份位置并保留服务器外副本 | 与程序发布包独立管理，按恢复策略保留 |

目录是首版部署建议，物理分离是已确认约束。同一台服务器／同一块磁盘可以采用上述独立目录，不能宣称这同时提供磁盘故障隔离。后续挂载独立数据盘／卷时仍保留此边界。

- 存档和数据库是持久业务数据，不允许写入源码目录、程序发布目录、output/、临时目录或相对工作目录。
- 数据路径通过显式配置提供；缺失或指向程序目录时启动失败，不悄悄回退到程序旁边创建数据库／存档。
- 部署只更新程序并切换当前入口，不使用覆盖程序目录的方式携带玩家数据，也不递归清理包含数据目录的共同父目录。
- 数据库结构通过版本化迁移更新，应用与结构兼容性单独验证；回滚程序不自动回滚或删除玩家数据。
- 使用容器时，镜像只含程序；数据库、存档及必要身份密钥挂载独立持久卷，重建容器不删除卷。
- P0 的隔离源码、构建和诊断报告属于临时验证工件，不是正式玩家存档；它们不得成为以后正式数据的默认目录。

P1/P2 必测：创建账号和对局 → 保存 → 替换程序／删除旧版本 → 重启 → 原账号与对局仍可恢复；验证数据目录独立、发布包不含数据、运行账号不能写程序目录，并独立执行备份恢复。

### 8.1 最小持久化对象

| 对象 | 主要数据与约束 |
|---|---|
| 账号 | 玩家 ID、账号标识、密码哈希、状态、创建时间 |
| 会话／邀请码 | 哈希凭证、归属、到期、撤销／使用状态 |
| 对局 | 所有者、状态、版本、规则／内容版本、完整存档 |
| 已处理请求 | 所有者、请求 ID、规范化请求摘要、原结果；唯一约束 |
| 战斗任务 | 战斗 ID、对局和版本、冻结输入、对手、seed、状态、租约、重试次数 |
| 战斗结果 | 战斗 ID 唯一、权威结果、回放信息、输入／输出摘要、结算标记 |
| 对手快照 | 来源账号／对局／轮次、版本、参战数据、有效状态、创建时间 |
| 本局匹配记录 | 已选对手、战斗 ID，支持重复规避与审计 |

先采用关系字段加版本化 JSON 负载，避免将所有领域类型直接交给通用序列化器。账号、状态、版本与索引字段显式建列；是否进一步拆分根据查询与测量结果决定。

### 8.2 完整对局存档

存档必须覆盖英雄与资源、卡牌和技能实例、双棋盘位置、永久成长与 Modifier 来源、宝石、任务、身份变化、轮／回合、遭遇候选与历史、商店商品及刷新状态、导师／宝石访问、待领取奖励、随机状态、已执行的一次性结算及待完成战斗引用。

以上是审计清单，不是当前模型字段的完整替代；P2 逐个审查所有可变字段并制作映射表。展示 Snapshot、完整存档、对手快照与战斗输入分别定义职责。恢复不得重新随机生成商品或丢失 Modifier 来源，从而引发重复奖励或无法精确撤销。

### 8.3 协议约束

- 所有状态修改携带 requestId 和 expectedMatchVersion；账号身份从认证上下文取得。
- 同请求 ID、同内容返回原结果；同 ID、不同内容拒绝。
- 服务器生成价格、随机数、实例 ID、对手和结算数据，客户端只提交操作意图。
- 命令白名单对应现有具体用例，不建立允许任意改字段的接口。
- 明确整数、decimal、ulong、StringName 和字典的编码规则；seed 使用无精度损失的编码，禁止经浮点数中转。
- 协议显式区分协议版本、存档格式版本、内容版本和战斗规则版本。
- 摘要基于规范排序和稳定编码；不得对无序字典或平台相关文本直接计算“确定性哈希”。
- 错误码至少区分未认证、无权限、版本冲突、操作非法、版本不兼容、排队、限流和暂时不可用。

### 8.4 API 草案

| 行为 | 建议接口 |
|---|---|
| 注册／登录／续期／退出 | POST /v1/auth/register、login、refresh、logout |
| 创建／获取当前对局 | POST /v1/matches；GET /v1/matches/current |
| 提交操作 | POST /v1/matches/{id}/commands；内部只允许显式命令类型 |
| 确认 PvP 参战 | POST /v1/matches/{id}/battles |
| 获取战斗状态／结果 | GET /v1/battles/{id} |
| 获取回放 | GET /v1/battles/{id}/playback |
| 健康检查 | 存活／就绪接口；公网响应不暴露内部诊断 |

接口路径为草案，P1/P2 输出字段、认证、错误与幂等契约后冻结。读取不得推进随机数或发放奖励。怪物战同样由服务端执行和结算，不能成为绕过权威状态的入口。

## 9. 异步 PvP 与事务流程

### 9.1 提交参战

1. 校验账号归属、对局版本、当前遭遇和参战资格，拒绝未完成必需选择的状态。
2. 服务端从合法对局冻结参战快照，禁止客户端上传任意英雄数值和卡牌属性。
3. 从同规则／内容版本、同轮次的候选中排除本人，尽量排除本局已遇来源；无候选则使用同版本、同轮次的预置测试构筑。
4. 在事务中固定对手、战斗 ID、双方输入、seed、任务和对局待结算状态。提交后才向执行器派发。
5. 首版建议参战后冻结本局可变操作，直到该战斗完成结算；确认请求重试不能重选对手。

测试构筑由服务端受控夹具生成并标明来源，不混入真实玩家统计，也不作为正式卡牌 Definition 的第二数据源。具体构筑与重复匹配放宽顺序在 P4 明确；不自行跨轮匹配。

### 9.2 执行与结算

任务状态：Pending → Running → Completed；暂时失败按有界次数重试，无法恢复则进入 Failed 并可诊断。Running 带租约和执行令牌，进程失联后可以回收，过期执行器不能覆盖新结果。

执行器读取不可变输入并调用同一模拟器，生成结果。结果提交时校验任务令牌、输入摘要及预期对局版本，使用数据库事务：

- 唯一写入战斗结果；
- 通过现有应用结算用例应用永久变化、任务、奖励、PvP 胜场、声望与结束状态；
- 保存完整新对局和新版本；
- 记录结算成功并关闭任务；
- 发布该轮开战前的合法参战快照供后续匹配，而不是用战后成长覆盖旧快照。

任务可重复执行，业务效果只能提交一次。任务与快照在同一数据库时尽量使用同一事务，避免先提交结果再异步重复发奖。结算中失败整笔回滚；提交成功但 HTTP 响应丢失时重试读取原结果。

采用“按同一已提交存档重新执行结算产生候选状态，再一次提交”的模式，避免将数据库事务长时间占用于战斗模拟。规则进程与数据库之间的原子边界必须在 P2 先验证。

### 9.3 断线与恢复

- 提交前断线：重新读取对局，必要时使用原请求 ID 重试。
- 排队或计算时断线：任务继续；重登读取同一战斗 ID。
- 结算后回放前断线：重复获取已存结果，不再次应用结果。
- 服务重启：恢复 Pending 与租约过期任务，完成已固定战斗。
- 战斗技术失败：保持冻结输入与对手，可修复后重试；不按失败请求直接判玩家输。
- 跳过、暂停或重复播放只影响客户端展示，不推进服务器结算。

## 11. 容量验收方案

以下阈值是首轮建议，需在测试前冻结。压测从客户端外部网络测量，明确地区与延迟；必须纳入真实 3 Mbps 出口或等效限速，不能仅在 localhost 测试。

| 场景 | 初始负载模型 |
|---|---|
| 阶梯在线 | 50 → 100 → 250 → 500 个账号，各稳态至少 15 分钟 |
| 构筑操作 | 500 人，平均每人 10 秒一次状态修改，约 50 次/秒；包含读取与真实业务比例 |
| 高频操作 | 每人平均 5 秒一次，约 100 次修改/秒，作为压力边界探索，不直接替代真实模型 |
| 持续战斗 | 初始模型：每人每 5 分钟一次战斗，约 1.67 场/秒；怪物与 PvP 分别测量 |
| 战斗峰值 | 50 人在 10 秒内提交战斗，同时保持普通操作 |
| 重连峰值 | 100 个账号在 30 秒内重新认证并恢复对局 |
| 长时间运行 | 500 人混合模型至少持续 2 小时，观察积压、内存和数据库增长 |
| 故障 | 杀死规则进程、重启 API、短暂断开数据库、丢弃响应后重试 |

初始模型不是对现有玩家行为的事实断言。封测后用匿名化聚合数据调整操作和战斗间隔，怪物战不能遗漏。

建议通过标准：

- 常规操作端到端 P95 ≤ 500 ms、P99 ≤ 1.5 s；大快照和回放单独统计。
- 非预期服务端错误率 < 0.1%；业务拒绝、限流、压测器错误单列，不用于掩盖故障。
- 持续战斗模型下队列不持续增长，提交至结果可获取 P95 ≤ 5 s；上述峰值下 P95 ≤ 15 s。必须同时报告回放可播放等待时间。
- 连续运行无 OOM、无持续换页抖动，CPU、内存、磁盘、出口和数据库连接均保留测得的运行余量。
- 不丢存档、不越权、不重复经济操作、不重复结算；正确性要求为零违反。
- 每类请求记录响应字节数，出口预算以分钟均值和短时峰值分别报告；月流量根据实测工作负载和在线时段推算。

容量估算采用实测单场 CPU 时间及每秒到达量。增加并发不能突破 CPU 总量，且可能增加内存；记录包含回放生成的总成本。若 500 人失败，报告满足指标的最大实测人数与瓶颈，不用猜测替代结果。

## 12. 运维、发布与版本

### 12.1 日志与监控

关联 requestId、玩家内部 ID、matchId、battleId 和版本。监控请求延迟／错误、任务积压与最老等待、战斗时长／失败、数据库连接与慢查询、CPU／内存、磁盘增长、出口速率和月流量。日志不得包含密码、完整令牌或敏感请求体。

磁盘先设置告警与轮换；保留周期在 P0 测量后定值。不同规则版本分别清理对手池和过期回放，进行中对局依赖的输入与结果不可被提前删除。清理任务必须可审计并限定批量。

### 12.2 备份与恢复

首版建议目标：数据恢复点不超过 24 小时、恢复服务不超过 2 小时；这意味着单机严重故障可能丢失最近一天进度，需要在封测说明中明确。若要求更低损失，增加更频繁备份或连续归档并测量资源成本。

数据库每日自动备份到服务器之外，备份加密、设置保留数量，并在首次封测前完成一次独立恢复演练。只生成备份文件而未恢复，不算通过。密钥与运维配置有独立恢复路径；云盘快照不能替代数据库恢复验证。

### 12.3 发布流程

构建 → 自动验证 → 测试部署 → 备份 → 停止新战斗入队／排空或冻结任务 → 数据迁移 → 发布 API 和规则版本 → 冒烟测试 → 开放请求。

首版建议一次只开放一个内容／战斗规则版本；进行中旧版对局采用短维护期保留旧版执行环境直至结束，或事先明确结束／迁移政策。不能升级后直接用新 Definition 重解释旧存档。若保留多个版本超出 4 GB 预算，则限制更新窗口，不悄悄跨版本复算。

回滚需要代码和数据库兼容；不可逆迁移不能仅回退二进制。记录部署版本、存档版本、内容指纹和恢复步骤。密钥不提交 Git；不默认推送 main，也不在本文任务中执行提交或部署。

## 13. 风险、待确认事项与决策门槛

| 风险／问题 | 处理方式与决策点 |
|---|---|
| 3 Mbps 不足 | P0 测体积、P5 测混合出口；优化负载或升级带宽 |
| 战斗生成大量状态 | 同时测事件／状态体积与内存，确定回放格式和保留周期 |
| Godot 与 API 运行依赖 | P0 验证常驻规则进程，不先做大范围解耦 |
| 存档遗漏临时访问／Modifier 来源 | P2 全字段审计、往返与后续操作一致性测试 |
| 任务重试引发重复收益 | 请求唯一约束、版本条件与结果事务共同保证 |
| 发布破坏旧对局 | 固定版本，发布前确定旧局策略与资源预算 |
| 同时在线误当同时计算 | 分开在线、请求、战斗和出口指标 |
| 单机故障 | 外部备份、恢复演练和明确维护窗口 |

实施前仍需确认，但不阻止本文规划：

1. 邀请码＋账号密码是否作为首版登录方案；每个账号是否只允许一个进行中正式对局。
2. 域名、服务器区域、CPU 架构、流量计费方向及超额处理。
3. 是否接受建议性能阈值、备份损失窗口与维护窗口。
4. 测试构筑的具体内容、同轮候选不足时的重复规避放宽顺序。
5. 内容更新时旧对局继续、迁移或结束的具体产品政策。

若新增正式术语，先在 GLOSSARY 登记再落实需求；若实施发现实际缺陷，按项目约定登记 BUG_LOG。本文列出的风险不等同于已发现代码 bug。
