# Project_Star 内容扩充实施计划

本文档记录核心玩法骨架完成后的内容扩充准备与新增系统实施顺序。通用规则以 `docs/design/GAME_DESIGN.md` 为准，架构边界以 `docs/engineering/ARCHITECTURE.md` 为准，术语以 `docs/design/GLOSSARY.md` 为准。

## 1. 目标

- 将英雄、卡牌、遭遇等内容定义拆分为低冲突结构，支持多人或多个代理并行扩充。
- 新增不占棋盘格的被动技能系统。
- 新增按战场卡牌组合触发的套装效果系统。
- 新增英雄收入属性和每轮收入结算。
- 为卡牌和技能建立统一的同级实例合并升级规则。
- 所有新系统继续复用通用 Ability、Effect、Modifier、Command、Result 和 Domain Event，不为单个技能、套装或卡牌编写专属规则类。

## 2. 已确认规则

### 2.1 内容并行扩充

- 英雄、卡牌和遭遇定义按类型分目录。
- 英雄不使用标签；`Human` / `Mechanical` 等标签只用于卡牌分类。
- 每个具体内容使用独立文件，避免所有内容集中修改同一文件。
- `DefinitionRegistry` 继续通过反射发现内容，不增加需要多人共同维护的中央注册列表。
- 并行内容任务原则上只新增或修改自己负责的定义与对应验证；共享规则变更必须先合并，再开展依赖该规则的内容工作。

建议目录：

```text
scripts/Content/
├── Heroes/
├── Cards/
├── Skills/
├── Sets/
├── Encounters/
└── Shared/
```

`Shared/` 仅保存已被多个内容定义复用的配置或构造辅助，不提前建立抽象。

### 2.2 被动技能

- 技能独立于卡牌和双棋盘，不占用卡牌格子。
- 技能和卡牌一样可由任意内容入口获得；所有来源调用统一的技能获得用例，不能为单一来源建立专属技能规则。
- 技能与卡牌一样采用定义与实例分离：`SkillDefinition` 保存不可变内容配置，`SkillInstance` 表示玩家实际拥有的独立技能。
- 每个技能实例具有独立 `EntityId` 和独立属性集；实例变化不得回写定义。
- 技能效果与卡牌被动能力复用同一套事件触发、目标选择和效果执行机制。
- 技能随所属一方进入战斗快照，战斗结果保持确定性和可回放。
- 禁止用隐藏卡牌或虚拟棋盘位置模拟技能。
- 技能能力来源必须能与卡牌来源区分，事件日志需要保留来源 key 或实例标识。

### 2.3 套装效果

- 每张卡牌最多属于一个套装。
- 套装归属是卡牌只读身份数据，套装 key 使用 `StringName`。
- 只统计战场区卡牌；备战区卡牌不计入套装数量。
- 相同 `CardKey` 的多张卡牌只计数一次。
- 达到多个阈值时效果累计生效，不只取最高档。
- 效果默认仅作用于该套装的战场卡牌；特殊目标由套装效果描述明确指定，可以是其他卡牌、全体战场卡牌或英雄。
- “全体卡牌”仅包含战场区，不包含备战区。
- 套装效果不限于数值加成，可以组合通用 Modifier、状态、被动能力及其他通用效果。
- 非数值效果的生命周期由每条效果描述决定，不设统一默认持续时间。
- 棋盘变化后重算非战斗套装效果；战斗开始后使用不可变快照，不读取之后的棋盘最终值。
- 战斗内卡牌被临时或永久摧毁，不改变本场已经生成的套装快照，已生效的套装效果继续有效。
- 每个阈值效果具有稳定的来源标识，重复重算不能重复叠加；失去阈值时只移除该阈值贡献。

示例：

```text
战士套装
- 2 个不同 CardKey：攻击力 +10
- 3 个不同 CardKey：攻击力再 +50
```

战场满足 3 个不同 `CardKey` 时，两档效果同时生效，总贡献为 `+60`。

### 2.4 英雄收入

- 新增 `Income / 收入` 英雄对局属性，默认值为 `5`。
- 每轮开始时，通过应用用例为玩家增加等同于当前收入的 `Wealth / 金钱`。
- 收入可以被对局内通用效果或 Modifier 调整。
- UI 不直接结算收入；结算必须产生可验证的领域事件或结果。
- 相同对局状态必须得到相同收入结算结果，且同一轮不得重复发放。

### 2.5 卡牌与技能合并升级

- 卡牌和技能实例默认等级为 1，但定义可以指定其他初始等级；普通等级为 1～4，且定义不必提供全部普通等级；部分定义可以额外提供第 5 级配置。
- 获得卡牌或技能时，若玩家已有相同定义 key、相同等级且未满级的实例，则合并并提升已有实例等级，而不是再保留一个同级实例。
- 两个同级实例合并后提升 1 级，新获得的实例被消耗。
- 允许连续合并：一次获得触发升级后，若升级后的等级仍存在另一个同 key、同等级且未满级的实例，则继续合并，直到没有可合并实例或达到 4 级。
- 同时存在多个可合并候选时，选择 `EntityId` 最小的实例，保证结果确定。
- 4 级实例不能再参与合并，任何合并都不能产生 5 级；再次获得同 key、同等级实例时，正常保留为新实例。
- 5 级不是所有定义必有的等级，不增加额外传奇字段。只有显式提供第 5 级配置的定义，才能通过特殊获得途径直接创建 5 级实例；5 级实例不能参与合并。
- 合并修改实例，不得修改对应的不可变 Definition。
- 卡牌与技能使用同一套合并决策规则，各自通过应用用例提交获得操作。
- 合并目标的选择和连续合并顺序必须稳定，不能依赖 List、HashSet 或 Dictionary 的偶然遍历顺序。
- 获得结果必须明确区分“创建新实例”和“合并升级已有实例”，供棋盘、商店和 UI 正确处理。
- 卡牌通过合并升级时不需要为新卡寻找棋盘位置；只有确实创建新卡实例时才执行自动放置和容量检查。
- 卡牌和技能定义分别保存各等级的数值与能力配置，升级后按新等级刷新实例；等级变化不得硬编码到具体卡牌或技能类之外的专属流程中。

## 3. 领域模型方向

### 3.1 技能定义与归属

新增独立的 `SkillDefinition`，保存技能身份和被动能力组合。`EntityFactory` 根据定义创建具有独立 `EntityId` 和属性集的 `SkillInstance`；玩家对局状态通过独立 `SkillInventory` 保存已拥有技能，不与 `CardInventory` 混用。`BattleSetupFactory` 将双方技能实例复制到 `BattleSideSetup`。

战斗层将当前只支持卡牌的能力来源扩展为通用战斗能力来源，至少区分：

- 卡牌来源：具有卡牌实例、区域、摧毁状态和卡牌战斗状态。
- 技能来源：不占区域，不因卡牌摧毁而失效，不接受仅作用于卡牌自身的目标。

两类来源共用 FIFO 队列、连锁截断、事件日志和 Effect 解析。不得复制一套仅供技能使用的战斗模拟器。

### 3.2 套装定义与计算

新增独立的套装定义，包含：

- `SetKey` 和展示名；
- 按数量升序保存的阈值；
- 每个阈值对应的可复用能力组合。

卡牌身份保存可选的 `SetKey`。套装求值器以战场快照为输入，先按 `CardKey` 去重，再按 `SetKey` 计数，输出稳定排序的已激活阈值。求值器只计算结果，不直接修改棋盘或实体。

阈值解锁的持续属性能力由应用用例根据求值结果精确 Apply / Remove Modifier；战斗触发能力写入 `BattleSetup`，由战斗层执行。套装定义不得读取其他卡牌已经计算完成的最终数值。卡牌描述、技能与任务解锁所表达的效果也均通过能力组合实现，不创建平行规则系统。

任务基础能力已实现：定义提供条件与次数，卡牌实例独立保存进度；战斗胜利可推进战场区和备战区任务，解锁后的能力仅随战场区来源卡牌生效。正式任务及其他条件待具体内容需求确定；“胜利一场战斗后攻击力 +100”只在验证入口使用。

### 3.3 收入结算

新增 `GameAttributeKeys.Income`，由英雄属性集提供默认值。轮次推进用例在轮开始边界调用收入结算，按“轮次 + 玩家”保证幂等，并通过玩家资源入口增加 Wealth。

收入不是身份字段，不放在英雄 Node 或 UI 状态中；它属于对局内可调整属性。

### 3.4 通用合并升级决策

建立纯函数合并决策器，以“获得的定义 key、等级、最大等级”和玩家已有实例快照为输入，输出创建新实例或升级指定实例的计划。应用用例负责原子提交计划。

卡牌升级后重算该实例依赖自身等级的基础值，并保留其 EntityId、棋盘位置和可追踪 Modifier；技能升级后同样保留 EntityId，并刷新由等级决定的能力参数。失败不得消耗获得来源、金钱或已有实例。

## 4. 实施顺序

本节状态按 2026-09-23 当前仓库源码核对；标记为“待确认”的规则会影响玩法或数据模型，确认前不猜测实现。

### 阶段 A：清理占位内容与建立目录约定

状态：**现有内容拆分已完成**。旧 `StarterDefinitions.cs` 不存在；正式英雄、卡牌、怪物和遭遇已按类型拆分；试玩与本地对手从注册表选择内容，验证入口使用内部验证定义。技能和套装目录在对应系统落地时建立。

1. 删除原 `StarterDefinitions.cs` 中仅用于早期验证的英雄、卡牌和遭遇。
2. 验证入口改用内部验证定义，不依赖正式内容。
3. 试玩与本地对手取消对占位 key 的硬编码，按稳定 key 顺序读取注册表中的正式内容。
4. 后续正式内容按英雄、卡牌、技能、套装和遭遇目录分别使用独立文件。

验收：构建通过；正式内容为空时试玩给出明确提示；新增正式内容后可被反射注册发现；Godot 内现有验证不依赖正式内容数量。

### 阶段 B：英雄收入

状态：**已完成**。

1. 在术语和游戏设计文档登记 Income。
2. 增加收入属性 key，并为英雄定义提供默认值 `5`。
3. 实现轮开始收入结算用例和领域事件。
4. 将收入加入只读对局快照和试玩界面状态。
5. 验证默认收入、修改后收入、跨轮结算和重复调用幂等性。

验收：每个有效轮开始边界只增加一次当前 Income 数值，UI 不能直接修改 Wealth。

### 阶段 C：卡牌合并升级与通用合并基础

状态：**通用合并决策器及卡牌、技能的获得与升级已实现；Godot 验收待执行**。

1. 建立卡牌和技能共用的纯函数合并决策器与稳定目标选择规则。
2. 改造 `AcquireCard`，返回创建或升级的判别结果。
3. 调整商店与自动放置：可合并升级时不要求空棋盘格。
4. 卡牌升级后按新等级刷新基础值与能力，同时保留原实例 ID、棋盘位置和可追踪 Modifier。
5. 增加同 key 同等级、不同等级、满级、多个候选和连续合并验证。
6. 技能定义与实例完成后，使用同一决策器接入 `AcquireSkill`。

验收：卡牌遵循已确认的合并规则；升级保留原实例 ID；新实例才占用卡牌格；交易和获得失败不留下部分修改；通用决策器可以在技能系统完成后直接复用。

### 阶段 D：通用能力来源与被动技能

状态：**代码已实现；Godot 验收待执行**。首版已确认为仅支持被动技能，任意内容入口统一调用获得用例。

1. 在术语、游戏设计和架构文档登记 Skill。
2. 建立 `SkillDefinition`、`SkillInstance`、`SkillInventory`、工厂创建和定义注册验证。
3. 将战斗能力来源从卡牌专用模型改为卡牌/技能通用来源。
4. 将技能写入战斗快照并接入被动事件匹配。
5. 增加授予技能的应用用例和只读快照字段。
6. 增加至少一个通用测试技能，验证其不占格且能触发。

验收：技能不出现在卡池或棋盘；空棋盘时技能仍可按规则触发；相同输入日志一致；回响不能形成技能与卡牌之间的无限连锁。

### 阶段 E：技能合并升级

状态：**代码与验证入口已实现；Godot 验收待执行**。

1. 使用阶段 C 的通用合并决策器实现 `AcquireSkill`。
2. 技能升级后保留原实例 ID，并按新等级刷新能力参数。
3. 增加技能同级合并、连续合并、4级封顶和5级不可合成验证。

验收：卡牌与技能遵循完全一致的合并决策规则；任何合并都不能产生5级实例。

### 阶段 F：套装系统

状态：**通用核心已实现，阶段未完成**。已具备套装定义与注册、可选卡牌归属、战场 `CardKey` 去重求值、累计阈值、持续属性能力的精确 Modifier 重算，以及战斗触发能力来源。示例战士套装仅是验证数据，不进入正式内容池。其他非数值效果及正式套装内容待具体描述后接入。

1. 在术语、游戏设计和架构文档登记 CardSet。
2. 为卡牌身份增加可选 `SetKey`，并验证每张卡最多属于一个套装。
3. 建立套装定义、阈值定义和注册验证。
4. 实现纯函数套装求值器和 `CardKey` 去重。
5. 接入棋盘变化后的 Modifier 重算。
6. 将战斗触发型套装能力写入 BattleSetup，并复用阶段 B 的通用能力来源。
7. 增加累计阈值、移除阈值、重复卡牌和备战区不计数验证。

验收：示例战士套装在 2 张时只获得 `+10`，3 张不同卡时累计为 `+60`；重复同名卡不增加计数；卡牌移出战场后精确移除失效阈值的贡献。

### 阶段 G：并行扩充首批内容

状态：**部分内容已存在，批次未完成**。已有帕拉帝恩英雄、卡牌、野猪怪物、遭遇及正式技能“突袭”“冲撞”；套装内容依赖阶段 F，首批内容范围仍需补齐。

共享系统稳定后按以下方向并行：

| 工作流 | 主要修改范围 | 依赖 |
|---|---|---|
| 英雄与初始属性 | `Content/Heroes/` | 阶段 B |
| 卡牌与能力组合 | `Content/Cards/` | 阶段 A |
| 被动技能内容 | `Content/Skills/` | 阶段 D |
| 套装与套装卡牌 | `Content/Sets/`、`Content/Cards/` | 阶段 F |
| 怪物与遭遇 | `Content/Encounters/` | 阶段 A |
| 内容验证 | `Presentation` 验证入口 | 对应内容批次 |

每个并行批次必须声明自己新增的 key，避免跨批次 key 冲突；不得同时修改同一个具体内容文件。

## 5. 待确认规则

开始对应阶段前必须确认以下事项：

### 被动技能

- 已确认：技能可从任意途径获得，统一走 `AcquireSkill`；技能实例属于当前对局，随新对局创建重新建立，与卡牌归属的生命周期一致。
- 已确认：首版仅允许被动能力，禁止冷却型主动技能。

### 套装效果

- 已确认：效果影响“全部卡牌”时不包含备战区；计数与目标范围都仅覆盖战场区。
- 已确认：默认仅影响该套装的战场卡牌；特殊目标必须在效果描述中明确指定。
- 已确认：非数值效果按各条描述确定生命周期，不设全局统一时长。
- 已确认：永久摧毁或战斗内临时摧毁都不影响本场已生成的套装快照，套装效果继续有效。

### 英雄收入

- 已确认：第1轮开始发放收入；创建对局并选择英雄后、生成第一个遭遇前结算。
- 已确认：后续收入在进入新轮时结算，先于该轮遭遇候选生成。

### 卡牌与技能合并升级

- 已确认：卡牌升级后按目标等级配置刷新基础战斗数值与能力，保留当前价值、实例 ID、棋盘位置和 Modifier。
- 已实现：技能等级配置分别保存基础战斗值与能力；升级保留实例 ID，并按目标等级刷新基础值与能力。

## 6. 固定交付与验证

每个阶段均需：

1. 先确认本阶段待确认规则，不夹带下一阶段功能。
2. 同步更新 `docs/design/GLOSSARY.md`、`docs/design/GAME_DESIGN.md`、`docs/engineering/ARCHITECTURE.md` 和本计划。
3. 新增的标识性 key 使用 `StringName`，身份字段进入属性集只读分区。
4. 新能力和效果必须可被多张卡、多个技能或多个套装复用。
5. 更新 Godot 内验证入口，并覆盖确定性、重复施加和精确移除。
6. 运行 `dotnet build`，再执行 Godot 内人工验证。
7. 发现 bug 时登记 `docs/quality/BUG_LOG.md`。
8. 不修改 `.godot/`，不让项目引用或打包 `ref/`。
