## 2. 里程碑与优先级

| 顺序 | 阶段 | 范围 | 退出标准 |
|---|---|---|---|
| 1 | M1：异步 PvP 可玩切片 | 最小账号、Linux 规则、权威存档、操作服务化、真实玩家快照对战、重连恢复；对应服务器 P0～P4 | 两个独立账号通过正常构筑流程产生和消费真实对手快照，战斗只结算一次，重启后继续；小规模邀请测试可重复完成 |
| 2 | M2：切片稳定与体验收口 | 集中修复切片反馈、完整人工对局、必要界面与回放问题 | 能完整完成至胜利／失败终局并重开，无阻断、丢档、重复收益或回放误导 |
| 3 | M3：内容扩充 | 根据切片反馈补卡牌、英雄、技能、怪物、导师、遭遇、套装与原画；安排整体 UI 更新 | 每批需求明确、定义和专项通过，并在真实联网流程中试玩，不以卡牌数量代替体验验证 |
| 4 | M4：扩大封测 | 500 人混合负载、带宽与流量、运维与版本演练；对应服务器 P5 | 当前或升级后的配置通过约定容量指标，再开放相应规模 |
| 暂缓 | 非主线专项 | 宝石全面专项、未安排的视觉打磨与世界观问题 | 等明确恢复或影响当前主线时再排期 |

500 人目标保留。M1 就测单场成本、协议体积和小规模稳定性，M4 再做完整容量认证；如果准备提前扩大测试，必须提前完成相应规模的压测。阶段顺序不允许将资金篡改、越权、存档损坏等正确性问题推迟到 M4。

## 3. M1：切片执行队列

### 3.1 先确定切片基线

- [ ] 固定一批现有内容及其版本，用正常选角、商店、遭遇和怪物战走到每轮第 8 回合 PvP；不新增英雄、卡牌或专属玩法。
- [ ] 先检查当前正式排程与候选是否能完成这条路径；如有实际缺口，只做必要补齐，不扩大为内容扩充批次。
- [ ] 建议默认复用现有正常玩法路径和已可达功能，避免另建一套简化规则。若需要关闭部分入口或缩小可选英雄，必须明确测试范围，不静默改变正式玩法。
- [x] 确定首版测试为邀请码注册＋密码登录，每账号一局进行中的正式对局；云端系统与 x86_64 架构已核实。
- [x] 每账号一局已在P2数据库唯一索引及创建事务中落实。
- [ ] 确定内容更新时的旧局政策；当前只允许相同规则版本恢复，其他版本保留存档并返回409。

### 3.2 按纵向闭环推进

- [ ] S1：在 Linux 运行现有规则，验证 Windows／Linux 确定性与序列化往返，测量耗时、内存和输出体积（P0）。
- [ ] S2：最小账号、认证、HTTPS、服务守护与基础日志（P1）。
- [x] S2 后端：账号、邀请码、会话、低权限服务守护及账号数据恢复；HTTPS、客户端登录与凭证安全存储继续待办。
- [ ] S3：登录 → 创建 → 购买一张卡 → 保存 → 重启 → 恢复，完成请求去重与版本冲突（P2）。
- [x] S3首条API操作链：创建→选店→购买→数据库存档→重启恢复；客户端面板已有后续链，其他访问状态继续待办，不勾选整个P2。
- [x] S3客户端首条链：Main联网面板与应用／HTTP适配支持登录→创建／恢复→购买→任务查询→结果→第二轮；客户端超时保留原请求，冲突读取最新状态，历史回执不回退当前局。完整棋盘／回放和鼠标云端整局试玩仍待办。
- [x] S3后续回合：离店→下一回合候选→再次选店，保留随机、历史及收入／经验结算游标；并发／重试不重复推进。
- [x] S3怪物战：正常商店路径→固定怪物准备→重启恢复→权威结算→领奖→第5回合；结果与奖励持久化、并发／重试防重复。仅结果摘要，完整回放待办。

- [x] S3选项事件：校场／酒馆／垃圾场及既有探险通用入口、固定访问／展示选项、一次结算、结果恢复和离开；探险引出怪物不重复推进，首轮正常路径到达第8回合候选。
- [x] 程序与玩家数据独立存放；同规则程序更新／回滚／清理后账号、对局、PvP任务与快照保留，独立数据库备份恢复通过。跨规则／结构升级仍需正式政策。
- [ ] S4：将切片中全部可达的状态修改接入服务器；覆盖构筑、奖励、遭遇、怪物战及轮次推进，不留下客户端权威入口（P3）。
- [ ] S5：固定对手与 seed、持久任务、权威模拟、原子结算、真实快照入池及客户端回放（P4）。
- [x] S5后端：固定输入／对手／seed、持久任务与租约接管、事务外模拟及一次原子结算；发布开战前真实快照，发生轮声望和终局统计正确。
- [ ] S6：两个账号交叉验证真实匹配、空池补位、被挑战方不变、断线重试与服务重启；完成小规模邀请试玩及一次备份恢复。
- [x] S6后端：两个正常构筑账号双向匹配并跨轮继续，空池／越权／重试／过期租约／提交回滚及PvP数据备份恢复通过；客户端断线体验及邀请试玩待办。

接续顺序：先将已有联网快照与操作接入完整原生棋盘，并补成长／技能详情和完整回放；新增UI按HTML先行。随后补导师／宝石及高轮次操作覆盖、旧局版本政策，配置HTTPS后进行小规模邀请试玩。当前面板与会话适配继续复用，不另建本地权威存档；容量清理和500人负载按开放规模安排，不提前扩充内容。

每一步先跑通一个可观察闭环再扩大覆盖；不要等所有接口写完才首次接客户端。字段、协议、事务与故障清单见[服务器计划](ASYNC_PVP_SERVER_PLAN.md)。

### 3.3 M1 完成定义

- [ ] 两个独立账号能登录、创建和恢复各自对局；账号隔离正确。
- [ ] 至少一个账号通过正常流程完成首轮 PvP，再继续到下一轮；匹配至少一次使用另一真实账号留下的合法快照。
- [ ] 空池按确认方案使用同版本同轮测试构筑，被挑战账号进度不变。
- [ ] 购买、奖励、移动、成长和战斗结果由服务器校验，重复与并发请求不产生额外收益。
- [ ] 断线、响应丢失和服务重启后仍读取同一场战斗，不重抽对手、不重复结算。
- [ ] 能看到真实阵容和可理解的回放／结果；输入不被 UI 阻断；新增联网 UI 按 HTML 先行流程实施。
- [ ] 记录实测小规模人数、请求／战斗成本和数据体积；备份恢复通过。不得据此宣称支持 500 人。

## 4. 缺陷如何插入主线

BUG 事实、根因与状态只维护在 [BUG_LOG](../quality/BUG_LOG.md)。以下是调度规则，不擅自关闭历史记录。

| 顺序 | 工作 | 安排 |
|---|---|---|
| 随 M1 立即处理 | 越权、丢档、重复扣款／奖励／结算、无法完成构筑或进入 PvP、结果不一致 | 发现即阻断当前阶段，登记、修复并做相关验证 |
| M1 路径预检 | BUG-361 获取／右键／旧节点门控，BUG-224 出售确认 | 先复现切片实际路径；若阻断立即修，否则带证据留到 M2 |
| 相关验证时处理 | BUG-346 轮初奖励夹具，BUG-275 原画传递与占位 | 影响当前必要验证时修正并补证据，不能为变绿跳过失败检查 |
| M2／M3 UI 收口 | BUG-127／362 整体视觉与棋盘、194 灼伤样例、282 背景、285 缩放截图 | 依最新 HTML 与当前交互核对是否仍成立；实际遮挡或命中问题提前处理 |

不要求 M1 前清空所有历史视觉缺陷，但 M1 的正确性和可玩性门槛不得降低。不得将检查失败直接认定为玩法 bug，也不得无复现依据认定只是夹具过时。
